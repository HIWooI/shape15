## 1. 목적

RGB 카메라 한 대로 사람을 보고, **로봇(K1, 23-DOF)이 따라 할 목표 자세를 실시간으로**
만들어 내는 것. 두 개의 출력이 있다:

1. **표시** — MuJoCo에 로봇이 사람을 따라 하는 모습
2. **정책 참조** — 다운스트림 전신 정책(TWIST 계열, `shape14`)이 먹을 50 Hz 참조 모션
   (관절 위치 23 + 속도 23 + torso 방향 6)

제약은 **지연**이다. 데모이므로 접지·자기충돌·속도한계는 정책의 몫으로 미룬다.
목표 로봇은 K1이고, G1은 교사가 ~10배 빨라 아이디어를 싸게 검증하는 용도로만 쓴다.

## 3. 여기까지 온 경로

### 3.1 지연 — 파이프라인을 갈라 해결 (완료)

원래 구조는 soma-retargeter(사내 리타게터)를 30프레임씩 묶어 호출해 870 ms가 걸렸다.
per-frame 미분 IK(PyRoki)로 바꾸고, IK를 **별도 프로세스·CPU**로 분리했다. 인지는
torch/GPU, IK는 JAX/CPU라 가상환경이 배타적이기도 했고, 분리한 덕에 GPU 경합과
warp/torch CUDA 그래프 충돌이 함께 사라졌다.

화면 멈춤은 별개 문제였다. 인지가 워커의 답을 **기다리는** 구조라 워커가 한 번 밀리면
카메라까지 멈췄다. 논블로킹 IPC(`IKLink`)로 바꾸니 프레임 간격 최대 **4017 → 308 ms**.
이걸 검증하려 했더니 기존 측정 도구가 라이브와 다른 경로를 타고 있어서(자체 블로킹 교환,
워커 렌더 없음) 측정 도구부터 고쳐야 했다.

### 3.2 정확도 — IK를 버리고 증류로 (완료)

44.8°에서 시작해 단계별로:

| 단계 | K1 오차 | 무엇을 했나 |
|---|---|---|
| 초기 IK | 44.8° | 위치 14점만으로 미분 IK |
| + twist 널스페이스 | — | 위치가 결정 못 하는 비틀림 DOF를 0 근처로 당김 |
| + 상수 오프셋 | 26.75° | SOMA와 로봇의 관절 영점 차이를 상수로 흡수 |
| 증류 MLP (plain) | 14.94° | 교사 출력을 흉내내는 네트워크 |
| + residual 4블록 | 13.97° | 그냥 깊게는 악화, 잔차+LayerNorm이라야 이득 |
| + interp 합성 데이터 | 10.71° | 실제 자세들의 블렌드로 학습셋 확장 |
| + 미러 증강 | **10.21°** | 좌우 반전 쌍을 추가 |

**결정적 발견은 "학생이 부족한 건 용량이 아니라 정보"였다.** 14개 점을 입력으로 주면
15.4°에서 정체하고 폭·깊이·데이터·시간 컨텍스트 어느 것도 듣지 않았는데, 교사가 실제로
소비하는 `body_pose`(SOMA 76관절 회전, 라이브에서 공짜로 나온다)를 주자 한 번에 9.5°로
떨어졌다. 우리는 스켈레톤 전체를 읽는 대상을 14개 점으로 흉내내고 있었다.

### 3.3 교사 결함 — 하루를 태운 사건 (해결)

라벨 품질을 **수치로만** 검사했다. 네트워크가 라벨을 0.18°까지 암기하고 최근접 이웃끼리
라벨 차이가 1.8°였으므로 "라벨은 자기일관적이다 → 교사는 정상이다"라고 결론냈다.

사용자가 사람 vs 교사 나란히 놓은 영상을 보고 **왼다리가 사람과 안 맞는다**고 지적했다.
자기일관성은 정확성이 아니다 — 같은 입력에 항상 같은 답을 주면서 그 답이 틀릴 수 있다.

추적해보니 `soma-retargeter` 서브모듈이 PR#1에 고정돼 있었고, 그 시점 K1 설정은
`_provenance`에 스스로 "G1 IK objective policy and G1-style target frames"를 쓴 **실험
후보**라 적혀 있었으며 `feet_stabilizer_config`가 G1 것을 가리켰다. 업스트림 PR#3이
K1 전용 feet stabilizer와 프록시 바디를 이미 추가한 상태였다.

| clip 17 전체 2,418프레임 | 병리 프레임 |
|---|---|
| PR#1 (쓰던 것) | 50.4% |
| **PR#3 (업그레이드)** | **1.0%** |
| PR#3 + post_processing 강제 ON | 44.4% (원작자 설정이 맞았다) |

업그레이드 후 전체 데이터셋 병리율 26% → 6.6%, 교사 속도 1.2 → 10 fps. 오염된 K1 라벨·
모델·오프셋은 전량 삭제하고 재생성했다.

### 3.4 합성 데이터 — 샘플링 방식이 전부 (완료)

교사는 SOMA 파라미터의 결정론적 함수이므로 영상 없이 라벨을 만들 수 있다. 처음엔 관절
범위를 1.5배로 넓혀 균일 샘플링했는데(`--mode box`) **무효**였다 — 사람이 취하지 않는
자세를 넣으니 교사가 다리를 관절 한계로 밀어 라벨의 41.3%가 병리가 됐다.

`--mode interp`로 바꿨다: 키프레임을 **실제 자세 두 개의 블렌드**로 만든다. 새로운
조합이면서 사람 매니폴드를 벗어나지 않는다(병리 0.0%).

| 합성 | 병리 | 학생 오차 |
|---|---|---|
| 없음 | — | 14.26 ± 0.12° |
| box m1.5, 24클립 | 41.3% | 14.46° |
| interp blend 0.35, 8클립 | 0.0% | 11.74 ± 0.07° |
| **interp blend 0.6, 8클립** | **0.0%** | **10.79 ± 0.07°** |
| interp blend 1.0, 8클립 | 0.0% | 11.57 ± 0.05° |
| interp blend 0.35, **24클립** | 0.0% | 12.18 ± 0.26° |

반직관적인 것 둘: **양을 늘리면 나빠진다**(합성이 실데이터를 수적으로 압도하면 학습이
그쪽으로 치우친다. 1:1이 최적), **blend는 중간값이 최적**(작으면 새 정보가 없고 크면
평균으로 쏠린다).

### 3.5 팔→다리 누설 — 미해결

사용자가 라이브에서 **팔만 들었는데 다리가 반응한다**고 지적했다. 측정했다:

| 팔 관절 입력만 섭동 | 다리 출력 변화 (평균) | 다리 최대 |
|---|---|---|
| ±10° | 1.87° | **31.6°** |
| ±30° | 4.56° | **38.3°** |
| ±60° | 7.89° | **63.8°** |

원인은 리타게터가 아니라 **단일 MLP 구조**다. body_pose 228차원을 받아 23개 관절을
한꺼번에 내므로, 입력의 팔 부분만 바뀌어도 다리 출력이 함께 움직인다.

여기서 **판단 착오를 했다.** "한쪽 다리만 반응한다"는 관찰에 이끌려 좌우 대칭성을
목표로 잡고 미러 증강을 넣었다. 결과는 좌우 균형(5.05/4.61 → 4.76/5.13)이었지만
**합계 누설은 9.66 → 9.89°로 줄지 않았다.** 사용자가 정확히 지적한 대로 "이제 양쪽이
반응"하게 만든 것이다. 대칭성이라는 엉뚱한 지표를 최적화했다.
(미러 증강 자체는 정확도를 10.79 → 10.21°로 개선했으므로 모델은 유지할 가치가 있다.)

**해결 완료.** 다리 전문가에게 팔 입력을 아예 주지 않으면 누설이 구조적으로 0이 된다.
`distill.py --arch parts`로 정식 편입했고, 최고 성능 레시피를 한 명령으로 재현한다:

```
.venv-ik/bin/python distill.py data/big4_k1.npz --features pose --width 1024 \
    --arch parts --extra data/synth_interp_k1.npz --mirror \
    --model models/k1_retarget_parts.pt
```

| 구조 | 전체 오차 | 팔 ±10° 섭동 시 다리 변화 |
|---|---|---|
| 단일망 res4 (+미러) | 10.21° | 평균 1.87°, **최대 31.58°** |
| **부위별 입력 차단 전문가** | **9.14°** | **정확히 0.000000°** |

부위별: 다리 5.93°(입력 66차원), 팔 13.85°(198차원), 몸통 0.46°(36차원).
정확도가 오히려 1.07° 좋아졌다 — 각 전문가가 관련 없는 입력에 흔들리지 않기 때문으로
보인다. CPU 추론은 2.56 ms로 단일망(0.3 ms)보다 느리지만 42 ms 루프에서 무시할 수준.

**그래도 다리는 움직인다.** 팔 입력만 인위적으로 흔드는 합성 검사는 0.000000°였지만,
사용자가 실제 화면에서 다리 움직임을 계속 지적했다. 그 검사가 틀렸다 — 실제 인지 출력은
팔↔다리 입력 상관이 +0.718, 팔↔몸통 +0.815라 팔을 들면 다리·몸통 입력이 같이 움직인다.
누설 경로는 팔 입력이 아니라 **몸통 입력**이었다.

측정 도구를 만들었다: 다리 관절을 완전히 고정한 채 상체만 움직이는 합성 테스트셋
(`data/legstatic_test_k1.npz`, 4 스탠스). 여기서 나오는 다리 움직임은 전부 누설이다.

### 3.5.1 몸통을 어깨에서 자르기 (`--part_in tight`)

`fixtures/soma_part77.npy`의 "torso" 13관절에는 **쇄골(11, 39)과 머리 체인(4-10)이
포함**돼 있다. 쇄골은 팔을 들 때마다 회전하므로, 다리 전문가는 팔 관절을 한 개도 안 보면서
팔의 움직임을 실시간으로 받고 있었다. 척추(1,2,3)만 다리에 주고 쇄골·머리는 팔·몸통에만
주도록 잘랐다.

| 모델 | 홀드아웃 | 다리 std | 다리 프레임간 |
|---|---|---|---|
| 교사 (정답) | — | 2.546° | 0.1555° |
| `parts` (wide) | 9.14° | 4.110° | 0.2836° |
| **`--part_in tight`** | **9.01°** | 3.946° | **0.2394°** |
| `--fuse` (wide) | 9.11° | 4.138° | 0.2867° |
| `tight --fuse` | 8.99° | 3.951° | 0.2406° |
| `tight` + 다리고정 학습데이터 | 9.60° | **3.474°** | **0.2217°** |

다리 전문가 입력을 66 → 39차원으로 **줄였는데 오차가 5.93 → 5.69°로 좋아졌다.**
쇄골·머리는 다리에게 정보가 아니라 노이즈였다. 화면에서 실제로 보이는 프레임간 떨림이
−16%다. `tight`가 기존 기본값을 세 지표 전부에서 이기므로 `models/k1_retarget.pt`를
여기로 옮겼다.

**융합 보정층은 기각.** 조립된 23각도 → 256 → 256 → 23 델타를 얹어봤지만 9.14→9.11,
9.01→8.99로 시드 편차 수준이고 떨림은 wide에서 오히려 늘었다. 23차원 병목에는 각 전문가가
놓친 정보가 없다. `--fuse`로 남겨두되 기본은 끈다.

다리고정 학습데이터(`data/synth_legstatic_k1.npz`)는 떨림을 가장 많이 줄이지만
홀드아웃을 0.6° 판다. 떨림이 정확도보다 중요해질 때 쓸 카드로
`models/k1_retarget_tight_legstatic.pt`에 남겼다.

영상: `outputs/tight_split.mp4` (SOMA 다리고정 | 교사 | parts | tight | tight+다리고정),
`outputs/legs_static_compare.mp4`.

### 3.6 shape10 리타게터 도입 검토 — 하지 말 것 (결론)

조사 결과 **shape10의 soma-retargeter가 바로 PR#1**(`e29a992`)이다. 우리가 8/14에
지운 그 버전이고, 우리 것(PR#3)의 직계 조상으로 4커밋 뒤다.

| | shape10 (PR#1) | 현재 (PR#3) |
|---|---|---|
| 라벨 병리율 | 26% | 6.6% |
| hip_roll 좌/우 비 | 2.99x | 1.79x |
| feet stabilizer | G1 것을 K1에 사용 | K1 전용 |
| `ik_iterations` | 180 | 24 |
| K1 URDF/MJCF | **바이트 동일** | 바이트 동일 |

"iteration을 180으로 올리면 비대칭이 나아지지 않을까"라는 가설은 죽었다 — shape10이
바로 그 설정이고 2.99배였다.

조사 중 **위험을 하나 발견해 제거했다**: GEM-X 인덱스가 여전히 PR#1을 기록하고 있어서
누가 `git submodule update`만 실행해도 조용히 되돌아갈 상태였다. PR#3으로 커밋해 고정했다.

shape10에서 가져올 만한 것은 하나뿐이다 — **ai_sapiens 0.1.1**(`c2880e8`, 우리는 0.1.0).
K1 `ros2_control` TCP→UDP 수정과 RadioMaster 채널 라벨 수정이 들어 있다. 리타게팅과는
무관하므로 실기 단계에서 가져오면 된다.

### 3.7 좌우 비대칭의 진범 — 데이터였다

`left_hip_roll` std가 오른쪽의 1.79배라 교사를 의심했으나, **미러 테스트로 무죄를
증명했다**: `teacher(mirror(x))`와 `mirror(teacher(x))`의 불일치가 평균 **0.62°**,
중앙값 0.05°. 리타게터는 좌우 대칭으로 동작한다.

클립별로 보면 비대칭이 사라진다:

| clip | 좌/우 비 |
|---|---|
| 0, 2, 4, 11 | 0.60~0.69x (오른쪽이 더 큼) |
| 1, 6, 16 | 0.85~0.92x |
| 7, 17 | 1.07~1.21x |
| **5 (태권도)** | **1.94x** |
| **14 (응원단)** | **1.75x** |

전체 1.79배는 clip 5·14가 만든 것이고, 그 둘은 std가 다른 클립의 5~10배라 통계를
지배한다. 그리고 그건 실제로 한쪽 다리를 쓰는 안무다.

앞서 "사람 입력은 대칭"이라 판단한 근거(발 위치 std 792.9 vs 792.6 mm)도 잘못이었다 —
**std는 좌우를 구분하지 못한다.** 왼발이 올라가든 오른발이 올라가든 같은 값이 나온다.

## 6. 부가 정보

### 반드시 알아야 할 함정 셋

1. **인지는 재현 불가능하다.** SAM-3D-Body 토큰 워커가 백그라운드 스레드라 어느 프레임에
   어떤 토큰이 붙는지 실행마다 다르다. 같은 영상으로 데이터셋을 다시 만들면 body_pose가
   평균 0.011 rad 달라지고 이전 수치와 비교할 수 없다. **`data/`의 npz를 보존해야 한다** —
   레시피가 아니라 파일이 자산이다.
2. **홀드아웃은 클립 단위로.** 같은 클립의 인접 프레임은 거의 같아서 프레임 단위 분할은
   무의미한 숫자를 낸다. 모든 수치는 마지막 2클립(taeguk_1st, video.mov, 4,697프레임)을
   빼고 나머지 13클립(4,699프레임)으로 학습한 것이다.
3. **CPU 네트워크는 `torch.set_num_threads(2)`가 필요하다.** 기본값(코어당 1개)이면
   Isaac 같은 이웃 작업과 경합해 0.09 ms짜리 forward가 60 ms가 된다. 실측 700배.
